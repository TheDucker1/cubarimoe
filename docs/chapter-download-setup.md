# Configure and run encrypted chapter downloads

The design is in [encrypted-chapter-downloads.md](encrypted-chapter-downloads.md). Progress and verification are recorded in [implementation-progress.md](implementation-progress.md).

## Required private configuration

Normal Django startup, including management commands, deliberately fails until required configuration is provided. There is no fallback password, S3 credential, or feature-disable escape hatch. Error messages name missing or invalid settings and their validation rules, never their values. DEBUG must remain false while these credentials are loaded.

The supported deployment is one web process and one Huey consumer with exactly one thread worker. Use the existing Python 3.8 environment and install the repository requirements. The additional packages are pinned to huey 2.5.2, pyrate-limiter 2.10.0, cryptography 44.0.3, and boto3 1.37.38.

The real configuration belongs outside Git, by default at `~/.config/cubarimoe/chapter-config.json` (`/root/.config/cubarimoe/chapter-config.json` for the current user). Only the empty `chapter-config.example.json` is tracked. The repository also ignores `chapter-config*.json` as a second precaution if a private file is accidentally placed in the checkout.

Create it once using the launcher:

```bash
cd /root/manga-reader/cubarimoe
./service init-config
nano ~/.config/cubarimoe/chapter-config.json
```

This generates the signing secret, master password, and salt directly into a 0600 file in a 0700 directory without printing them. It refuses to overwrite an existing file. Initial limits are 64 MiB per archive, 8 MiB per image, and 256 MiB disk cache (also at most 20 files); adjust for chapter size and available memory/disk. Fill the missing S3 endpoint, bucket, credentials, and region in your editor and confirm the addressing style. Missing values still refuse startup.

If you already created a private configuration, move that existing file to this location instead of generating different secrets. Preserve the existing password/salt/KDF settings and file mode 0600. No real private file is moved or generated by repository installation or tests.

The launcher reads this default location automatically; no export is needed. To use another location, pass `./service --config /absolute/path/to/private.json` (also supported for `init-config`/`setup`), or set `CHAPTER_CONFIG_FILE`. Keep actual credentials in the file rather than command arguments. The loader rejects symlinks, non-regular files, incorrect ownership, and group/world permissions.

Individual environment settings can override file settings. Values are not copied into the process environment when loaded from a file. Do not enable SDK debug logging or log the private file/environment.

Required fields:

| Field | Format |
| --- | --- |
| `SECRET_KEY` | Random Django session/signing secret of at least 32 characters |
| `CHAPTER_MASTER_PASSWORD` | Strong private password of at least 16 characters |
| `CHAPTER_KDF_SALT` | Base64-encoded random bytes, at least 16 decoded bytes; preserve permanently |
| `CHAPTER_S3_ENDPOINT_URL` | HTTPS endpoint without embedded credentials, query, or fragment |
| `CHAPTER_S3_BUCKET` | Private bucket; versioned or unversioned, with no retention preventing deletion |
| `CHAPTER_S3_ACCESS_KEY_ID`, `CHAPTER_S3_SECRET_ACCESS_KEY` | Credentials limited to this bucket/prefix |
| `CHAPTER_S3_REGION` | Region string accepted by the provider for SigV4 signing |
| `CHAPTER_S3_ADDRESSING_STYLE` | `path` or `virtual`, according to the provider |
| `CHAPTER_MAX_ARCHIVE_BYTES` | Positive maximum CBZ size, at most 536870912 bytes |
| `CHAPTER_MAX_IMAGE_BYTES` | Positive maximum image size, no greater than the CBZ limit |
| `CHAPTER_CACHE_MAX_BYTES` | Positive disk cache budget |

Generate secrets with a password manager or a local random generator and save them directly to the private file. Never paste real values into this documentation, commit messages, issue comments, or chat output. Changing the password, salt, or KDF parameters without re-encrypting stored objects makes them unreadable. Back up these configuration values and SQLite together.

Archive limits require RAM headroom: CBZ/ciphertext can coexist during encryption, and one web decryption may run while a download is being built. The disk cache stores only encrypted bytes. Its default 20-file limit also respects the configured byte budget. An object larger than the cache budget is served without being retained.

Remote names use `objects/<64 random hex characters>`, without extensions or chapter identifiers. New encrypted headers also exclude chapter identity/version. SQLite holds the mapping; back up it together with the private configuration. Choose a generic bucket name and keep the prefix `objects` (or another generic prefix). Object sizes/timestamps remain visible to the storage provider. Previously created objects retain their old names/format until explicitly replaced.

Optional settings use conservative defaults. `CHAPTER_RUNTIME_DIR` defaults to `.chapter-data` under the checkout; `CHAPTER_CACHE_DIR` defaults to its `cache` subdirectory. Overrides must be absolute, distinct paths in owner-only directories (0700). Keep this directory dedicated to chapter runtime data. The worker lock, Huey queue, and persistent limiter database reside under the runtime directory. Polling is every two seconds and archive decryption is limited to one request at a time per web process.

Request pacing defaults to a two-second gap after completion, one request per two seconds, and 300 requests per hour. Configure `CHAPTER_REQUEST_RATE_LIMITS` as increasing `[request_count, seconds]` pairs. Configure `CHAPTER_REQUEST_DELAY_SECONDS` for longer completion gaps. A 403 pauses upstream downloads immediately; an explicit Retry action clears blocking flags but preserves time deadlines and rate history. Retries and redirects pass through the same gate.

## Request settings

| Setting | Meaning |
| --- | --- |
| `CHAPTER_REQUEST_DELAY_SECONDS` | Minimum wait after each worker upstream request finishes, including metadata, redirects, retries, and image pages. Finite number, minimum 1 second. |
| `CHAPTER_REQUEST_JITTER_SECONDS` | Additional random wait in `[0, jitter]`; default 25% of the configured base delay. Finite, nonnegative; 0 disables it. |
| `CHAPTER_REQUEST_TIMEOUT_SECONDS` | Connect/read timeout for worker HTTP and storage requests; 1–300 seconds inclusive. This is not a whole-chapter deadline; read timeout measures inactivity. |
| `CHAPTER_MAX_RETRIES` | Failed-request attempt budget, including the first attempt; 3 means up to two retries. Positive integer, maximum 10. |
| `CHAPTER_MAX_BULK_ITEMS` | Maximum chapter identities per management API submission, not parallel downloads; maximum 1000. |
| `CHAPTER_REQUEST_RATE_LIMITS` | All `[request count, seconds]` budgets apply together globally and per host. Positive pairs with increasing counts and intervals. `[[1, 2], [300, 3600]]` means at most one request per two seconds and 300 per hour. |

A 60-second completion gap defaults to 0–15 seconds of additive jitter, so each persisted completion gap is 60–75 seconds. To choose explicitly, add `"CHAPTER_REQUEST_JITTER_SECONDS": 15`. Randomness never shortens the minimum delay or resets limiter/cooldown history. Huey schedules work and PyrateLimiter enforces budgets; application-level completion jitter is added explicitly.

A 60-second completion gap and the default rate pairs are compatible. The gap makes actual throughput roughly at most 60 requests per hour before request durations/backoff, so the 300/hour ceiling is normally inactive. A timeout of 300 is valid and does not add a delay to successful requests.

Startup errors now identify the specific invalid field without printing its value. An endpoint must include the `https://` scheme and hostname; a bare endpoint domain is not a complete URL. Environment overrides can take precedence over the private file.

## One-time setup and one-command startup

For a new installation, after filling the private configuration:

```bash
./service setup
```

This validates configuration, applies migrations, verifies storage with a read-only diagnostic, and prompts to create the staff/superuser account. If an account already exists, skip this setup action; ordinary startup also validates configuration and applies outstanding migrations. No migration is run before configuration validation succeeds.

Daily startup is one command in one terminal:

```bash
./service --allowed-host 10.121.15.2 --allowed-host localhost
```

The web server defaults to `0.0.0.0:8010`; use `--bind` to change it. Replace the allowed host with your actual VPN address; repeat the option for multiple addresses/names. No wildcard is needed. No separate activation, configuration export, worker terminal, or web terminal is needed.

The foreground launcher starts one Huey worker and one Django web process, and forwards their logs to the same terminal. Ctrl+C or SIGTERM stops both. If either child exits, it stops the other and returns a failure status so a service manager can restart the pair. It gives shutdown up to 30 seconds before terminating remaining children; unfinished jobs recover on the next start. A launcher lock prevents starting a second combined service; Huey's existing worker lock separately prevents a second download consumer.

Ordinary startup checks configuration and applies migrations without contacting S3. `setup` verifies S3, and the worker verifies storage before any upstream download. This permits cached chapter reading during a storage outage. The bucket must grant GetBucketVersioning plus GetObject/PutObject/DeleteObject for the configured prefix. Versioned/suspended buckets additionally need ListBucketVersions and DeleteObjectVersion (the provider’s equivalent permissions). The read-only diagnostic also checks version-list access. Single-object uploads and permanent deletion are supported.

Backblaze B2 keeps versioning enabled; “Keep only the last version” is a lifecycle rule, not disabled versioning. Version-aware cleanup lists every data version and delete marker for the exact recorded object key, deletes each by VersionId, and confirms none remain. Prefix lookalikes are never removed. Retries repeat remaining cleanup safely. Before replacing an unaccepted target after restart, old versions at that target are purged. Lifecycle settings need not be changed. Retention/permission failures leave the job failed/deleting for explicit retry, never reported as removed.

See [Backblaze lifecycle rules](https://www.backblaze.com/docs/cloud-storage-lifecycle-rules) and [S3 Delete Object](https://www.backblaze.com/apidocs/s3-delete-object) for provider semantics.

The current launcher uses the existing Django development server with DEBUG disabled, `--noreload`, and `--insecure` to serve local static files. This is the local single-user/VPN setup. Public deployment should replace that web-server component with a production WSGI/static setup. Never use test settings to serve real traffic.

## Running under systemd later

[deploy/cubarimoe.service.example](../deploy/cubarimoe.service.example) uses the same foreground launcher. Adjust its user, paths, and allowed host to your deployment. It contains only a configuration path, not secrets; the private file must be owned by the service user. The supplied paths and user match the current root-owned checkout.

When ready to install the unit:

```bash
sudo install -m 644 deploy/cubarimoe.service.example /etc/systemd/system/cubarimoe.service
sudo systemctl daemon-reload
sudo systemctl enable --now cubarimoe
```

Then manage the whole service with `systemctl restart cubarimoe`, `systemctl stop cubarimoe`, and view both processes' output with `journalctl -u cubarimoe -f`. The unit uses Restart=on-failure, a 45-second stop timeout, and KillMode=mixed so the launcher can stop its children before systemd cleans up any remaining processes. The example is not installed/enabled by this implementation.

Sign in with the staff/superuser account via `/admin/login/`. Open a series to populate server-resolved selection keys. Its table offers row Store/Remove buttons, checkboxes, a group selector, select-visible/all controls, and bulk actions. Choose the group explicitly; unavailable groups are skipped. The reader offers Store current chapter and Remove stored chapter. `/downloads/` shows the persistent queue, progress, cooldowns, cancellation, retry, and optional clear-all local archive cache maintenance.

Stored images are served by Django at `/stored-chapters/<chapter-key>/<archive-version>/pages/<page>`. Accepted chapter metadata replaces upstream URLs with these local URLs. Storage/decryption failures return an error rather than silently contacting upstream. The reader displays a stored-image failure message with a staff-only “Read from source instead” link; choosing it explicitly uses upstream pages without deleting the stored archive. Browser source reads retain their existing preload behavior and are outside the worker rate gate. Reading access follows the existing reader boundary; management endpoints require a staff session and CSRF checks. The private bucket never needs public image URLs.

## Verification without real credentials or upstream traffic

```bash
.venv/bin/python manage.py test downloads.tests --settings=downloads.tests.settings
node --check downloads/static/downloads/downloads.js
```

Test settings generate ephemeral secrets and isolated SQLite/runtime directories. Tests use fake image transport and object storage, so they do not touch the real bucket or upstream image hosts. They verify request timestamps, retry/redirect gating, persistent cooldowns, encryption authentication, acceptance/cancellation races, deletion, LRU behavior, and authenticated APIs.

Configuration can be verified locally, but actual provider behavior cannot be confirmed until the user supplies storage configuration. No live remote archive download/upload/delete is required to run this test suite.


## Browsing downloaded chapters and applying code updates

Sign in with your staff account and open `/library/` (the “Downloaded chapters” link in the site navigation, reader storage dialog, or queue page). Titles expand to show only ready stored chapters and translation groups. Search filters stored titles. Select all includes chapters under collapsed titles in the current search results; clear selection and bulk removal use the existing persistent deletion queue. Failed removal requests retain selection. Accepted removal requests disappear from this view; the queue reports actual completion/errors. Refresh the library to discover newly completed downloads.

Library chapter links open the original reader through `/library/read/<anchor-key>/<chapter>/<page>/`. Metadata comes from SQLite only, includes only stored chapters for that translation group, and uses local image URLs. No cover/source refresh is performed. Stale or missing cached source metadata cannot hide an otherwise ready stored chapter. The reader's title link returns to the library. `?upstream=1` cannot switch these routes to source reading; the source-fallback link is omitted. The normal series reader is unchanged. Library management requires staff login; stored reading retains the application's existing public reading boundary.

This update adds no dependency, configuration, or database migration. The service runs without automatic code reload. After updating the checkout, activate the new code with:

```bash
sudo systemctl restart cubarimoe.service
sudo systemctl status cubarimoe.service --no-pager
```

Use `sudo journalctl -u cubarimoe.service -f` for logs. `daemon-reload` is needed only after changing the systemd unit, not after ordinary application-code updates. The persistent queue survives restart; an unfinished chapter restarts from the beginning. Existing configured delays/rate-limit history remain in effect. If running directly in a terminal, stop `./service` with Ctrl+C and start `./service` again. Hard-refresh the browser after restarting if it keeps older styling.

Additional isolated checks: `node downloads/tests/frontend.js` and `node downloads/tests/library_frontend.js`.
